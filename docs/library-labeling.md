# Library labeling

`pharos labeling` prepares a library's conversation text for labeling by a large "teacher" model, offline, so the labels can later train a small local classifier. It is a deliberate command-line workflow: nothing runs when Pharos starts, captures, indexes or opens a page, and no command here writes the catalog.

This page covers preparation, planning, running labeling jobs and their status, exporting training data, and the smoke check of that export.

## Commands

```sh
pharos [--config PATH] labeling prepare --dir DIR [--catalog PATH] [--fresh-days 14] \
    [--limit-conversations N | --conversation ID ...] [--splits-from OLD_DIR] --catalog COPY --snapshot-copy [--allow-stale-shm] [--replace] [--dry-run]
pharos labeling plan --dir DIR --route claude|codex --model M --effort E [--items-per-request 4] \
    [--max-request-tokens 24000] [--max-request-chars N] [--include-duplicates] [--max-per-text N] [--concurrency 3] [--cohort C ...] [--split S ...] [--limit-items N]
pharos labeling status --dir DIR [--job NAME [--json]]
pharos labeling run --dir DIR --job NAME [--create --route claude|codex --model M --effort E [--prompt VERSION] \
    [--cohort C ...] [--split S ...] [--item ID ...] [--limit-items N] [--items-per-request 4] [--max-request-tokens 24000] \
    [--max-request-chars N] [--include-duplicates] [--max-per-text N] [--refusal-registry FILE] [--skip-oversize] [--create-only]] \
    --max-usd X [--concurrency 3] [--timeout 330s] [--retry-invalid 1] [--max-consecutive-failures 3] [--allow-unpriced] [--accept-served-model MODEL]
pharos labeling stop --dir DIR --job NAME
pharos labeling reconcile --dir DIR --job NAME [--retry-unknown] [--retry-failed] [--requeue-held] [--retry-suspected-refusals] [--retry-tool-use]
pharos labeling import-results --dir DIR --from OLD_DIR --job NAME [--refusal-registry FILE]
pharos labeling export --dir DIR --job NAME [--out DIR] [--replace [--force-replace]]
python3 tools/labeling_smoke.py EXPORT_DIR [--out model.json] [--report report.json]
```

- **prepare** reads one snapshot of the catalog and writes a dataset to `DIR`. It reads only a backup copy of a catalog, named with `--catalog PATH --snapshot-copy`; it never reads a live catalog. `--limit-conversations N` prepares a fixed sample of N conversations (those whose works are not mirrors, in the order of the SHA-256 of their IDs); `--conversation` prepares named ones. Either restriction is recorded, and the manifest then calls the result a restricted sample, not the library. `--dry-run` computes the same manifest and prints it as JSON without creating or writing anything. `--splits-from` keeps the splits an earlier dataset gave its conversations (see below). Progress (phase, counts, elapsed time) goes to standard error.
- **plan** reads only a prepared dataset and estimates a labeling run: how many requests, how many tokens, what it would cost, and how long it might take. It calls no model and writes nothing.
- **status** prints a dataset's manifest summary, or says that preparation is incomplete, and one line per labeling job. With `--job` it shows that job; `--json` prints everything (below).
- **run**, **stop**, **reconcile** and **import-results** create and run labeling jobs: see [Running a labeling job](#running-a-labeling-job). `run` is the only command that calls a model, and it calls one only within its `--max-usd` ceiling.
- **export** writes one job's results as training files: see [Training export](#training-export-labeling-export-v1). It reads the dataset in one read-only transaction and writes only the export.

Choose a dataset directory outside the catalog folder, for example `<library>/labeling/<name>`. A dataset holds private conversation text: its files are created readable only by you (0600, directory 0700). `prepare` refuses a directory that is not empty unless `--replace` is given, and `--replace` removes only a dataset's own files; it refuses a dataset that holds any labeling job, request or attempt records, so paid results are never lost. One command at a time can prepare into a directory (`DIR/.lock`).

## Reading the catalog

Preparation reads a backup copy, never a live catalog: a read transaction on a live catalog would hold back Pharos's checkpoints and writer for the minutes preparation takes. Pharos's own backup produces a copy: a checkpointed catalog file that nothing writes. Pass it with `--catalog PATH --snapshot-copy`; preparation opens it immutable (`mode=ro&immutable=1`), so SQLite reads only the main file and creates or touches no `-wal` or `-shm` beside it. Preparation refuses:

- the configured library's own catalog (compared as the same file, not by name), and any catalog whose folder holds `.pharos-service.lock` or `.pharos-use.lock` (a library's catalog folder; a backup's has neither);
- a copy with a non-empty `-wal`, since its main file is then incomplete;
- a copy with a non-empty `-shm`, which an open database always has, unless `--allow-stale-shm` says it is a stale file from the backup (use it only for a copy you know nothing has open).

Preparation fails, publishing nothing, if the copy's main file, `-wal` or `-shm` changed size or modification time while it was read, or a non-empty `-wal` appeared. The manifest records the copy's path, size, modification time and whether a stale `-shm` was allowed. Preparation never initializes, migrates or writes a catalog.

Preparation reads catalog schemas 7 (the tool ledger, which launches and question-tool answers come from) through the version this build writes. It refuses newer and older catalogs. An older catalog lacks some tables and columns. Preparation checks which, supplies them as empty for its own queries (temporary views on its connection), and says in the manifest's `coverage` what is missing and what that costs. For example, a schema-14 catalog has no normalized reasoning store, so its thinking is excluded (`reasoning_store_absent`) and the manifest says thinking is unavailable from that snapshot. A missing feature is never reported as a zero.

Human contribution comes from the existing authorship classifier ([Human authorship](human-authorship.md)), run in memory on the same snapshot rather than read from the stored ledger, so it covers exactly the snapshotted messages without waiting for or writing that ledger. The manifest records whether the stored ledger was current, for comparison only. Identity and lineage come from the usage rules: mirrored works are counted once, and each unit's canonical conversation, root conversation, execution run and delegation depth are those the Usage pages resolve, using the headless-run launches derived on the same snapshot rather than the stored launch ledger, which can lag behind new runs. A depth comes from the unit's agent session (its embedded session, or its conversation's main one); without one, the stored depth is used and marked `stored`, and a conversation whose parent is missing, conflicting or circular is marked unresolved.

The snapshot identity in the manifest is the start and end time, catalog path, schema version, SQLite `data_version`, the tool-ledger, authorship-input, authorship and reasoning-extraction generations, and the build (commit and executable hash).

## Units (`labeling-units-v1`)

A unit is one message. Labels are per message; sentence boundaries and byte positions are kept so later work can choose a smaller unit. Each unit belongs to one cohort:

| Cohort | Messages | Text labeled |
|---|---|---|
| `human` | user-role messages a person sent | the human pieces (below) |
| `agent_in_user_role` | user-role messages the classifier attributes to a script, headless run, other agent, TL1 or sub-agent, and user-role messages of an embedded sub-agent session | the message after its leading harness blocks |
| `agent_reply` | assistant and agent messages | the whole message |
| `delegation` | delegations and their results | the prompt or returned content, decoded from the stored JSON (`json-string-v1` over its encoded bytes); the whole record when it is not one string |
| `thinking` | retained reasoning, thinking and analysis | the whole text; summaries keep `reasoning_format` |

A delegation or result that repeats a message of the child it started is kept, with `duplicate_of` naming that message, so the two are never counted as independent events. Texts are compared with whitespace collapsed: equal to any child message, a child's first request containing the delegation's prompt, or a result containing the child's last reply. The manifest reports, for delegations and for results, how many had a recorded child and how many matched each way.

A forked conversation starts with a copy of its parent's history, which is excluded as `inherited_history` (with `duplicate_of` naming the parent message where one matches) before any cohort is chosen, so a person's message copied into a fork is never labeled again, and never as an agent's request. Unselected records are skipped on both sides. Where copies keep their original send times, every selected record sent before the fork's start is a copy and none sent at or after it is; each copied text record is matched to the parent record it repeats, in order where possible, and copies that match none are counted. Where they do not (the backup examined stamped copies at the fork: all 195 in-order matches were sent after the parent's record and at or after the fork's start), or times are missing, the child's text records are walked alongside the parent's in order, and the first difference ends the copy. When a copy differs from the parent early (a regenerated instruction message), the walk ends before the copy does; later records that repeat a parent message from before the fork, each parent message once, stay units but get `duplicate_of`, so `plan` skips them and training does not count them twice. Copied requests and replies are still context for the first new turn. The manifest's `duplicates.forks` shows which rule each fork used and counts those later copies. In the in-order case a new message identical to the parent's next record (a fork from an earlier point, then "continue") is still taken for a copy. Authorship treats every conversation with a parent as a sub-agent; for labeling, a continuation (a Codex filename fork, whose lineage is the root's own execution) is classified as the root's, so the person's new messages there are human.

Every other record is excluded and counted by reason in the manifest: messages in mirrored works, unselected branches, empty text, invalid UTF-8, tool calls and results, metadata, other roles (`system`, `developer`), and other kinds; `result` records (possible copies of the final reply); unavailable reasoning (redacted or encrypted, never inferred); thinking in conversations whose reasoning extraction is pending; answers to question tools (`AskUserQuestion`, `request_user_input`) that arrive as tool results, which become actions (below) or, when the result cannot be parsed, are counted as `question_tool_result_unparsed`, a coverage gap, split by who would have answered; messages the classifier gave no result (`authorship_missing`, for example one without a send time), which never fall back to the raw text; and the human-piece exclusions below. Exclusions of messages that could have been units are also kept row by row in the dataset.

## Human pieces (`human-pieces-v1`)

The classifier splits each user message into spans. Preparation gives each span a role:

- **Target** text may receive labels about the person: typed text (`estimated_typed`: what no other rule claimed, an estimate rather than proof), comments inside recognized page-feedback reports (`feedback_comment`), the person's own earlier messages sent again (`reused_own_message`, linked to the source; reuse inherits the source's attribution: the re-sent text is found in the source message and only the bytes that were target there, resolved the same way, stay target, while the rest, or text whose source is missing or cannot be matched, is context `reused_unverified`, so a re-sent log or old agent output never becomes the person's words), and one-click templates and slash commands (`reused_template`: no new words, but a real request).
- **Context** is material that helps interpret the person but is not theirs: quoted text (`quoted`, linked to the agent output it matches), likely pastes (`likely_pasted`), and attachment references. It is kept with its source but supplies no evidence.
- **Dropped** text is harness (instructions, generated report fields, question forms) and secrets.

The text a teacher sees is the target pieces in order. Other material between, before or after them is replaced by markers, one for each run of the same kind, so pieces are never joined into a sentence the person did not write:

- Context shows what the person is reacting to: `⟦quoted agent text, context only, 312 chars: "…"⟧`, with an excerpt of at most 300 characters (its head and tail when longer) and at most 1,200 excerpt characters per unit; markers after that budget give only the length. Kinds are `quoted agent text` (matches agent output), `quoted text` (lines quoted with `>`), `likely pasted text` and `attachment reference`.
- Dropped material gives only its kind and length: `⟦excluded: question form, 40 chars⟧`, `generated page feedback`, `harness text`, `redacted secret`.

Harness blocks that open a message are dropped without a marker, and so are leading `<in-app-browser-context …>` blocks, which authorship-v8 does not recognize and counts as typed (Human Words still does; a follow-up for that feature). These are counted as `unrecognized_harness_tags`. Each marker's byte range in the visible text is stored (`marker_ranges`), so evidence quoted from inside a marker can be rejected. Every piece keeps its exact byte range in the stored message. A JSON-encoded feedback comment is one piece over its encoded bytes, shown decoded (`json-string-v1`).

Anything the context redaction patterns match (API keys, bearer tokens, `token=` and similar URL parameters), in any cohort's text, becomes a dropped `redacted_secret` piece: it is never shown, excerpted or quotable. The manifest counts them.

There is no word-count threshold. A message that is only `?`, `+1`, a number or an emoji is kept: a deliberate short reply is meaningful. Punctuation left over after excluding copied material (a quote, a paste, unverified reused text) is excluded as `residual_punctuation`; next to an attachment, a secret or harness it is kept. A message with no target text is excluded as `no_target_text`, or as `action_only` when its only content was a question-form answer.

Answers to questions an agent asked are recorded as actions (`actions` table), never as labeled text:

- A prewritten option submitted as a flattened message (the question title followed by the option) is a `submitted_option` with status `recognized_question_form`: the question, the option as offered, the message that submitted it, the byte ranges of the question and answer lines, and the tool call that asked. Each answer line counts once, for the most recent matching question. The actor is the submitting unit's (a person's, or an agent's for an automated message).
- Answers in a question tool's result (`User has answered your questions: "Q"="A"`, Conductor's `User responses:` with one numbered line per question, or a JSON `answers` object) have status `tool_result_answer` and actor `human` only when the session was interactive when the answer arrived (a root's own execution, not delegated or launched, whose latest user message by then came from a person) and the answer responds to a question tool call recognized in the same conversation; otherwise actor `unknown` and status `tool_result_answer_unverified`. Each action records what its actor rests on (`actor_evidence`: `interactive_session_question_tool`, `automated_session`, `delegated_or_unresolved_run`, `no_user_message_before_answer`, or `flattened_question_form_message`), so consumers can choose. A tool result whose answers were also submitted as a flattened message is excluded as `tool_result_answer_duplicate`. The result message is the submission and the asking call (its message and call ID) the question; branch selection and inherited history apply first. Each answer is one `submitted_option` per selected option, or a `free_text_answer` with the text when the answer is not an offered option.

An answer recorded both as a flattened message and as the question tool's result (the same asking call and question) is one action: the flattened form, which has byte ranges, is kept. An unsubmitted default or a skipped question is not an answer. Results that hold no answer (`{"accepted": true}`, tool errors) stay the counted `question_tool_result_unparsed` gap; the manifest lists their forms (`actions.unparsed_shapes`, structure only, letters masked).

## Context (`context-v3`)

Each unit carries the context the measured prompts used: `Previous user request:` and the last 1,400 characters of the previous request unit's visible text (a person's or an agent's in the user role, so a sub-agent's replies see their assignment), then `Previous assistant message:` and the last 800 characters of the previous agent reply, both within the same agent session (the main session, or an embedded sub-agent's), (a part is left out when there is none), stripped and cut to its first 2,200 characters. API keys and tokens are redacted in each part before its tail is taken, so a cut can never expose part of one. A prompt shows the last 600 characters of that (`context_prompt`). Characters are Unicode code points. Context only ever comes from earlier messages. The dataset stores the rendered strings and the messages they came from.

The measured experiments built the same strings from the stored authorship ledger's typed spans, joined by a fragment marker, and from native capture files. `context-v3` differs from that historical construction (which DESIGN.md calls context-v1): the previous user request is the previous request unit's visible text, markers included, and an agent's request in the user role counts, where the measured extractor used only human typed text; context is kept per agent session (v2); and each part is redacted before it is cut, where the extractor redacted the joined string (v3; the output differs only when a secret is present). The catalog keeps no final or commentary channel, so a unit's channel is `analysis` for thinking and `unspecified` otherwise. Target text is not redacted.

## Long text (`chunking-v1`)

A unit's visible text longer than 6,000 characters is split into items of at most 6,000: at the last paragraph break in the second half of the window, else the last sentence end there, else the last space, else between characters. No cut falls inside a character, before a combining mark, joiner, variation selector or emoji modifier, between the two halves of a flag, or inside a marker. Nothing is truncated: the items join to the full text, and each records its range in the visible text and the byte ranges it covers in the stored message. A chunk holding only markers is attached to the item before it (or, at the start, after it), so every item holds target text, the teacher still sees the marker, and the items still join to the visible text; such an item can exceed 6,000 characters by the marker's length (`attached_marker_chunks`, `marker_chunks_attached`).

Sentence ranges of every target piece are stored against the stored message (`sentences`, `sentences-v1`: after `.`, `!`, `?` and similar marks followed by space, and at line breaks; a transformed piece is one range), so later work can choose sentence units. Long units are counted separately; merging their chunk labels is not yet validated.

## Families and splits (`splits-v1`)

Conversations that share text or execution form one family: mirrors and aliases, root and parent conversations, forks, delegated children, headless runs and the command that launched them, and conversations where the classifier found a re-sent or quoted passage from another, of any length, with a recorded source. Repeated lines do not link families: a reused instruction would chain unrelated work together. Identical text alone never links families: a stock reply or canned prompt would chain unrelated work together. Instead each item stores a hash of its target text (markers removed, lowercased, whitespace collapsed; `target_hash`). An item whose text occurs in more than one split is marked `cross_split_duplicate`, and a held-out item (dev, test, fresh) whose text of at least 40 characters also occurs in train is marked `seen_in_train`, which evaluation should exclude, as near-duplicate filtering does. Shorter repeated texts ("continue", "yes", "do it") recur by chance and are the short approvals evaluation must keep: they are marked `common_short_text`, a stratum to report separately, not to drop. The manifest counts all three. A family whose first message (the earliest message time of any of its conversations, not when a session was opened) is within `--fresh-days` (14) of the snapshot (of when a copy was taken, for a snapshot copy) is the `fresh` holdout; every other family is `train`, `dev` or `test` (80/10/10) by a hash of its ID (its smallest member's).

A family's ID can change when a new conversation links into it, and the fresh window moves with time, so a later preparation can assign a conversation to a different split. The dataset stores every conversation's split (`families`); `--splits-from OLD_DIR` keeps them: a family with a conversation the earlier dataset assigned takes that conversation's split, so a conversation that joins an old family inherits it, and only new families are assigned afresh. A family whose conversations the earlier dataset put in different splits goes to `quarantine`: it belongs to neither training nor evaluation. The manifest reports how many conversations inherited, joined an old family, or were quarantined. It also shows split coverage by cohort, provider, depth and length, and family sizes: the number of families with units, the largest and the top ten as shares of units, and each split's share of units.

## The dataset

`DIR/dataset.sqlite3` holds `units` (with the original message text and its hash, visible text and marker ranges, context, lineage, family and split), `pieces`, `sentences`, `items`, `actions`, `exclusions` (with `duplicate_of` for inherited history), `families` (every conversation) and `meta`. A finished dataset uses SQLite's rollback journal, so reading it (`plan`, `status`) leaves no files behind. `DIR/manifest.json` is written last, atomically, and only when preparation completed: a directory without it is incomplete, and `prepare.incomplete.json` records the attempt and, when it failed or was interrupted, why. The manifest holds the scope and options, snapshot identity, contract versions (units, pieces, marker, context, chunking, splits, taxonomy `candidate-0.3` and its SHA-256), counts by cohort, provider, depth and length, exclusions by reason, reasoning coverage, authorship status, duplicates, long units, invalid UTF-8, actions, split coverage, and a statement of the population it describes.

## Planning

`plan` skips delegation units that repeat a child's message (`duplicate_of`) and reports how many (`--include-duplicates` keeps them). It packs the selected items, in a fixed order, into requests of at most `--items-per-request` items whose estimated input, the fixed prompt overhead plus the items' text and context, stays within `--max-request-tokens` (24,000), and, when `--max-request-chars` is given, whose characters stay within it too. No request holds two items of one family (so of one conversation): the teacher must not see a conversation's later message, or another chunk of the same message, beside an item under "INDEPENDENT ITEMS"; the measured benchmark took one message per conversation. The packer takes, for each request, the first fitting items of new families within 256 items of the oldest unpacked one, so this costs requests: the plan reports `packing.requests_without_family_separation` and `added_requests` (on the 2026-10-27 sample, 18% of four-item requests mixed one conversation's items, 70% in a thinking-only dataset). `--max-per-text N` keeps at most N items with the same cohort and target text (counted in item-ID order, a deterministic choice spread across splits and time): automation prompts recur thousands of times verbatim (a title-generation prompt, for example), and labeling every copy buys nothing; the plan reports `repeated_text_items_skipped`. The default is no limit; for the full library run a limit such as 20 is recommended. An item that does not fit even alone is never sent oversized: it is listed in `oversize_items` and the command fails (chunking keeps items far below this). It then estimates tokens from measurements of 18 four-item requests at effort high on 2026-10-27: per request, about 14,300 input tokens of prompt, taxonomy, schema and CLI framing for the `claude` route (Haiku 5.5) and 16,100 for `codex` (Luna), plus the items at 3.6 ASCII characters per token and half a token per UTF-8 byte of any other character (1.5 for a CJK character, 2 for an emoji), a conservative bound for dense scripts; per item, about 1,006 output tokens for Haiku and 212 for Luna, reasoning included. Each constant has a flag (`--overhead-tokens`, `--output-tokens-per-item`, `--seconds-per-request`, `--chars-per-token`). The cost is priced with the price book built into Pharos for the named model on the day of the plan, at standard rates without cache or batch discounts; a model the book has no confirmed price for is shown as unpriced, never guessed. Runtime is the largest of the measured request time (17 s for Haiku, 10 s for Luna) over `--concurrency`, the input over an assumed `--tokens-per-minute` (2 million) and the output over a fifth of that, plus 25%, with a planning high of three times that. The plan prints every assumption; effort levels other than high are flagged as uncalibrated.

## Running a labeling job

A job labels a frozen selection of a dataset's items through one route, model, effort and prompt version, and keeps its ledger in the dataset (`jobs`, `requests`, `request_items`, `attempts`, `item_results`, `usage`). Those tables are not part of a prepared dataset, so `prepare --replace` refuses a dataset that has them.

```sh
pharos labeling run --dir DIR --job pilot --create --route claude --model claude-haiku-5-5 --effort high \
    --limit-items 200 --create-only                      # freeze and print the selection; no model call
pharos labeling run --dir DIR --job pilot --max-usd 2    # label it, spending at most $2
pharos labeling status --dir DIR --job pilot --json     # in another terminal
pharos labeling stop --dir DIR --job pilot              # or Ctrl-C
```

**Creating.** `run --create` selects items as `plan` does (in item-ID order; `--cohort`, `--split`, `--item`, `--limit-items`; duplicates skipped unless `--include-duplicates`; `--max-per-text`), skips every item a refusal blocks (below; each gets a `refused_elsewhere` result with no labels and its reason, so the export lists it), packs them with the same family-separating packer and limits into numbered requests, and prints the selection. The selection never changes afterwards: a later `run` without `--create` continues the same requests. If any selected item is too large for one request, creation fails and lists them: no job is created with items it could never send. `--skip-oversize` creates the job without them instead: each gets a `blocked_oversize` result, and status reports the job incomplete. `--create-only` stops after printing. `--prompt` chooses the prompt version (below); the job records it with the schema, taxonomy and dataset contract versions, the CLI's path and the version it began with. The version is asked again (`--version`) at every run start and recorded per run and per attempt, since CLIs update themselves during long runs.

**Running.** Requests are sent in order, at most `--concurrency` (3) at a time. Each attempt gets a directory `DIR/attempts/JOB/NNNNNN/ATTEMPT/` (0700) holding `prompt.txt`, `command.json` (the argv with the schema replaced by a reference to `DIR/contracts/schema-….json`, the prompt by its SHA-256; the environment is inherited and not recorded), `events.jsonl` (the CLI's stream, written line by line as it arrives, with Claude thinking blocks and Codex reasoning items reduced to their type and ID; usage is kept), `stderr.log` and, for Codex, `answer.json`. The run prints one line per finished request: its outcome, request counts by state, known spend, unknown-outcome exposure, rate and ETA. It ends when no request is pending, when stopped, or when it halts, which exits with an error saying why, records it in the job (`halted`, shown by status) and is resumed by running again:

- the spend ceiling would be exceeded (below);
- usage could not be priced;
- `--max-consecutive-failures` (3) attempts in a row ended `failed` or `unknown`, or as many requests in a row were refused, so a broken route, flag, login or prompt does not use up the job;
- an attempt failed with an authentication, rate-limit or quota error, or a connection error (recognized from the CLI's error text), at once;
- a model other than the requested one answered (below);
- an attempt's saved stream could not be written or synced: the attempt stays `unknown`, since a result without a durable receipt can be neither audited nor recovered;
- a successful terminal event carried no usage the runner could read (`usage_missing`): its cost is estimated, and spend can no longer be known;
- the ledger could not be read or written while leasing: nothing more is leased, attempts in flight finish and are recorded, then the run exits with the error.

**States.** A request is `pending`, `leased` (chosen by the runner), `submitted`, then `completed`, `invalid`, `refused`, `failed`, `unknown` or `held`; `stopped` is a request leased but not yet sent when a stop came. Each transition is one SQLite transaction, and `submitted` (with the attempt row) is written before the CLI starts, so no request is ever sent unrecorded.

- `completed`: a terminal event with structured output that passed validation for every item.
- `invalid`: structured output that broke the contract or any tool use. An ID set that is not exactly the request's (an ID missing, extra, repeated or without an ID) makes every item of the request invalid (`request_id_set_mismatch`; missing items stay `missing`), since the annotations may be misassigned. Otherwise only the offending items are invalid (a bad field, type or label), and valid items keep their results.
- `refused`: a structured refusal only: a refusal stop reason (even when no terminal event followed), a provider or CLI error whose own code or message states a refusal (word-bounded policy or refusal wording: Anthropic's "Usage Policy", which Claude Code reports in result text it writes itself with an `API Error:` prefix; OpenAI's `invalid_prompt`, content-policy and content-filter codes; an explicit "refusal" or "refused"), or a reply that is not JSON-like and opens with a refusal phrase. Model or corpus text echoed in a result never counts, and a connection error such as "Connection refused" or `ECONNREFUSED` is `failed`.
- `refusal_suspected`: refusal words in a reply that is not a clear refusal (for example cut-off JSON quoting "I can't get the build to pass"). Re-sent only by its own job, with `reconcile --retry-suspected-refusals`.
- `refused_elsewhere`: every item of the request was blocked before it was sent by a refusal (below).
- `waiting_suspicion`: held unsent because one of its items is, for now, a suspected refusal in another job; it returns to `pending` at the next run start (or a re-queue) and is checked again.

**What a refusal blocks.** A refusal of a request of one item is pinned to that item: its content key (the source message's hash and the target text's hash) is appended, durably, to the refusal registry before the ledger records the refusal, and no job of any dataset, on any route, sends that content again. The registry is one append-only file per library, by default `labeling-refusals.jsonl` in the directory that holds the datasets (`--refusal-registry FILE` on `run --create` and `import-results`; the job records it); each line names the key, dataset, manifest SHA-256, job, item, attempt and time. A refusal of a request of several items cannot be attributed to one of them: each item carries `refused_copacked_unresolved` and is blocked by its item ID only, in its dataset and in datasets that import from it (`import-results`), never by content, so identical texts elsewhere stay labelable. A suspected refusal holds the item's requests in other jobs (`waiting_suspicion`) only while it is that item's latest result in its own job; once that job resolves it, they can be sent. Refusals are checked when a job is created (blocked items are not sent: `refused_skipped`, each with a `refused_elsewhere` result), when each request is leased and again in the transaction that submits it (the registry is read fresh each time, and the dataset's own ledger checked too; blocked items leave the request with a `refused_elsewhere` result, and a request left empty is not sent), and whenever `reconcile` re-queues. A registry that cannot be read or parsed, or holds fewer entries than the job saw before, stops the run: refusals never silently stop applying. There is no override and no re-send path for refused items; re-sending co-packed ones is a deliberate operator decision outside this tool's defaults. Status (`coverage`) counts pinned refusals, co-packed blocked items, items refused elsewhere and requests waiting on a suspicion; `plan` reports the dataset's refused and co-packed items.
- `failed`: the CLI could not be started (`not_sent`: the only case known to cost nothing), or it reported an error as its terminal event (which may have been charged).
- `unknown`: the CLI ran but no terminal event came: a timeout (`--timeout`, 330 s), a crash, an exit, or a stop that had to terminate it; or the saved stream was not durable. The provider may have charged for it, even when the CLI printed nothing (`no_stream_events`, which `reconcile` explains). A Codex attempt whose last-message file (`answer.json`) was written without the turn's end is not unknown: the saved answer is validated as its result, flagged `answer_without_terminal`, and its cost stays estimated.
- `held`: the reported served model differs from the requested one. The items keep their labels with outcome `held` and issue `served_model_differs`, are not usable (export excludes them by default), and the run halts. The job then refuses to run until the operator decides: `run --accept-served-model MODEL` records the acceptance (with its time) in the ledger, returns the held items of that model to the outcome they had (`served_model_accepted`, the issue kept) and accepts later attempts it serves; or `reconcile --requeue-held` sends the requests again.

**Stopping and resuming.** `stop` (or SIGINT/SIGTERM; a stop requested while a runner is still starting applies to it) makes the runner lease nothing more and let in-flight attempts finish; after two minutes, or a second signal, they are terminated and become `unknown`. One runner runs a job at a time (`DIR/.run-JOB.lock`), and no runner, `stop`, `reconcile` or `import-results` runs while `prepare` holds the dataset. On start, a runner returns `leased` and `stopped` requests to `pending` and settles every `submitted` one from its saved stream: a terminal result there is validated and completed without sending it again (`recovered`), otherwise it is `unknown`. Before anything, the runner checks that this build and dataset still produce the job's frozen contract: the schema, taxonomy and prompt-template hashes stored at creation, and every unsent item's contract hash (which includes the prompt-template hash); on a mismatch it refuses, so one job never mixes contracts. A CLI process an earlier runner left behind is killed first, but only when its process group's leader is still the recorded process (same pid and start time); otherwise the attempt notes `possibly_orphaned` and nothing is signalled.

**Lingering processes.** The CLI runs in its own process group, in an empty private directory (`DIR/runner`; a run refuses to start if anything is in it). After its terminal event a CLI that is still running gets SIGTERM after 10 s and SIGKILL 5 s later, as does anything left in its process group after it exits. This cleanup is recorded in the attempt (`cleanup`) and does not change the outcome: a result that arrived stands.

**Retries.** Invalid or missing items are re-packed into a new request (`retry_of`) up to `--retry-invalid` (1) more times per item, also when a hold is released (in the same transaction). An attempt that used a tool is never re-sent automatically, since an injected instruction would get a second try: `reconcile --retry-tool-use` re-queues it. `unknown` and `failed` requests are never re-sent automatically: `reconcile` lists unknown, failed, refused, invalid and held requests with their receipts, and attempts whose cost is only estimated, and `--retry-unknown` or `--retry-failed` re-queues them explicitly. Their earlier attempts stay in the ledger and in spend. Refused items are never re-sent: a new job skips them (`refused_skipped`) and `import-results` carries them as refused (see what a refusal blocks, above).

## Spend

Every attempt's usage is stored per model, from the terminal event: for Claude each model in `modelUsage`, auxiliary models included (the one matching the result's `usage` takes that usage, which splits cache writes by TTL), and for Codex the turn's usage under the requested model, since Codex reports no model name. Tokens are normalized as everywhere in Pharos (`normalizeTokenCounts`: Claude's input excludes cache reads and writes, OpenAI's includes them; reasoning is part of output) and priced with the built-in price book on the attempt's UTC day (`priceBook.cost`), with the status `priced`, `assumed`, `partial` or `unpriced` and the model priced. The labeling model (the requested one, and any model the route reports serving) is priced only under its exact name: no family normalization or alias lends a snapshot or variant name the requested model's rates. A served model name the job did not ask for is stored as reported and priced as itself only when it was accepted (`--accept-served-model`, which re-prices its usage) and the price book has exactly that model; otherwise (held, re-queued, or accepted but not in the book) the row is `unpriced`, and its known tokens are estimated at an upper bound kept apart from the cost (`estimate_usd`, `estimate_basis` `upper bound: PROVIDER`: for each token category, the highest rate of any model of the same provider in the price book that day), counted as exposure, never as $0. The hold governs a served model (`--accept-served-model` or `reconcile --requeue-held`). The same estimate applies to any other usage that cannot be priced as itself (an auxiliary model the book cannot resolve, unattributed usage); such usage halts the run, and a restart stays blocked until an explicit decision: `--allow-unpriced`, recorded in the job's `decisions` with its time, covers the unpriced usage recorded before it. The highest known rate is not the unknown model's price, so the estimate never stands in for a decision. Usage that lacks input or output counts (a lone total, say) cannot be priced: it is `partial` and stays partial through any re-pricing, the attempt keeps its estimated exposure, and the run halts. The usage `modelUsage` attributes to the labeling model must cover the result's usage; any difference is recorded as an unpriced `unattributed:MODEL` row with an upper-bound estimate (exposure), the attempt is `usage_unexplained`, and the run halts. Auxiliary models, the CLI's own calls that did not produce the annotation, are priced through Pharos's standard resolution (model family and dated aliases), so `claude-haiku-4-5-20251001` prices as `claude-haiku-4-5`, recorded as the priced model; only if that fails are they bounded as above. Each usage row records its role (`primary` or `auxiliary`), and status shows auxiliary spend by model, so an unexpected extra call is visible. The rule is versioned (`pricing-v2`): a job priced under an earlier rule is re-priced from its stored tokens at the next run start. The reported model must equal the requested name exactly (Claude's `system/init` and message models; auxiliary models in `modelUsage` are expected): otherwise the request is `held` (above). Codex names no model in its stream, and `--ephemeral` keeps no session record that would, so Codex labels are always `served_model_unverified` (job, attempts and results): usable, with the flag carried into the results for export. Before trusting the route at volume, check the served model once by other means (for example one deliberately non-ephemeral request). Without an exact match between a model's `modelUsage` and the result's `usage`, a single cache-writing model takes the result's one-hour cache-write share; when several models wrote to the cache and the one-hour writes cannot be assigned, all their writes are priced at the one-hour (higher) rate and marked `assumed`. Failed and invalid attempts count.

The status shows, separately:

- **known spend**: the sum of priced costs (a `partial` cost is a lower bound);
- **partial or unpriced tokens**, by model: usage the price book cannot price, never treated as free;
- **possibly charged exposure**: the estimated cost, from the plan's calibration, of attempts that may have been charged but report no usage: `unknown` ones, `failed` ones that started, and results without usage. They stay in the job's spend after they are re-queued, since they may really have been charged;
- **in flight**: the estimate of leased and submitted requests;
- **CLI-reported cost**: what the CLIs said they cost, kept as evidence but not authoritative. A CLI older than the model it runs prices it wrongly (Claude Code 2.1.288 does not know Haiku 5.5 and reported $0.59 for pilot requests priced at $0.014). Tagged CLI diagnostics on stderr (such as `[claude-code:unrecognized_model]`) are stored per attempt and shown once in status as CLI warnings.

`--max-usd` (positive and finite) is required and is the job's lifetime ceiling, not one run's. Before each lease the runner adds known spend, the in-flight and possibly-charged estimates and the next request's estimate; if that exceeds the ceiling it leases nothing more, lets in-flight attempts finish, and halts with the breakdown. To continue, run again with a higher `--max-usd`. A model the price book cannot price does not start, unpriced usage halts the run after that attempt, and a job holding unpriced usage (other than a held served model's) or partial usage no exposure covers does not run again until `--allow-unpriced` records that decision (its spend is then unbounded).

## Validation (the publication contract)

An exit code or a terminal success is not enough. Each attempt's structured output is checked against the request: exactly the expected IDs (missing, extra and duplicate IDs are named), the required fields and no others, field types, labels from the taxonomy, and no label both accepted and uncertain. Each evidence quote is looked for in the item's visible text (CURRENT_TEXT): every occurrence is mapped to byte ranges of the stored message, through the target pieces (a quote inside a marker, outside target pieces, or only in the context is not evidence), checked to be the same bytes on character boundaries; a transformed piece maps to its whole encoded range. A quote may span target pieces only where their original byte ranges are contiguous; pieces that are adjacent only in the visible text (dropped text between them leaves no marker) would join words the author never wrote together, so such a quote is `spans_pieces`, not evidence. Every occurrence of a quote is recorded with its own status (`valid`, `in_marker`, `outside_target`, …); a quote that occurs more than once, in target text or a marker alike, is `ambiguous`. A quote found in target text and also in a marker or outside target pieces of CURRENT_TEXT is `ambiguous_mixed`: the response does not say which the teacher meant, so it supports no label. A quote that also occurs in the preceding context stays evidence (the prompt shows the context apart from CURRENT_TEXT); it is flagged `echoes_context` and counted in status (`quote_echoes_context`). An accepted label without valid evidence is flagged.

Each item gets one outcome: `usable`, `usable_with_evidence_issues` (kept, with its issues listed), `invalid`, `missing`, `refused` or `held`. Only the first two are training rows. Each result also stores, per accepted label, its evidence status (`labels_evidence`: `supported`, or why not: `in_marker`, `in_context`, `not_found`, `outside_target`, `missing`, …). Export treats only `supported` accepted labels as positives: a label whose only evidence is quoted or pasted material credits the person with someone else's act. Uncertain labels are stored apart and are never accepted labels; an empty accepted set is a result, a missing item is not.

## Prompts and routes

`prompt-candidate-0.3-questions-short` reproduces the measured prompt byte for byte (experiment.py `prompt(rows, 'questions', 'short')`: definitions, the leaf-label question checklist, the items as JSON with their sender, channel, the last 600 characters of context and whether it was cut), and the schema is the measured `schema()` as the CLIs received it. `prompt-candidate-0.3-questions-short-pieces-v1`, the default, adds one sentence saying what `⟦…⟧` markers are and that evidence never comes from inside one. A job uses one version for all its items, so results stay comparable.

- `claude`: `claude -p --model M --effort E --output-format stream-json --verbose --json-schema SCHEMA --tools "" --safe-mode --disable-slash-commands --no-chrome --strict-mcp-config --permission-prompts none --permission-mode dontAsk --no-session-persistence --session-id UUID --name "Pharos labeling" --prompt-suggestions false`, the prompt on stdin. The session name matters: without one, Claude Code 2.1.288 makes its own session-title call to an auxiliary model (claude-haiku-4-5, 5,000-7,000 input tokens per request in the 2026-10-27 pilot, more than the labeling call cost). The terminal event is `result`; the annotation is its `structured_output`.
- `codex`: `codex exec --ephemeral --ignore-user-config --ignore-rules --skip-git-repo-check --sandbox read-only --model M --config model_reasoning_effort="E" --config project_doc_max_bytes=0 --color never --json --output-schema FILE --output-last-message FILE` with `--config web_search="disabled"` and every tool feature that `codex features list` (codex-cli 0.155.0) shows enabled by default disabled: apps, plugins, shell_tool, unified_exec, multi_agent, browser_use, browser_use_external, computer_use, in_app_browser, code_mode_host, code_mode, image_generation, view_image, tool_suggest, skill_search, sleep_tool, goals, remote_plugin; the prompt on stdin (`-`). All of these names exist in that listing. What a worker may still have is whatever codex builds in without a feature switch (the model can, for example, still emit a plan or a web search item if the config key is not honoured); any such item in the stream makes the attempt invalid. The terminal event is `turn.completed` or `turn.failed`; the annotation is the last-message file.

Both run with the user's environment, so they use the CLI's own login; Pharos never reads, copies or records credentials. Sessions are not persisted, so labeling does not flood the captured library. Any tool event (other than Claude's `StructuredOutput`) makes the attempt invalid.

## Reusing results across snapshots

`import-results --dir NEW --from OLD --job NAME` refuses a job labeled under a schema, taxonomy or prompt template this build does not produce, and otherwise creates job `NAME`, in one transaction with its requests and imported results (every selected item is requested, imported or listed as oversize, or nothing is written), in a newly prepared dataset with the old job's route, model, effort, prompt and selection, and copies the old job's usable and refused results for items whose model-visible contract is unchanged: the hash of the prompt version, taxonomy, schema, sender, channel, context and CURRENT_TEXT. Their evidence is re-mapped to the new dataset's bytes. Every other selected item is packed as pending, for `run` to label.

## Training export (`labeling-export-v1`)

`export --dir DIR --job NAME` writes the job's items to `DIR/exports/EXPORT_ID/` (or `--out DIR`, which must not exist or be empty). It takes the dataset's shared lock (no `prepare` runs meanwhile), reads everything in one read-only transaction, writes into a temporary directory beside the target and renames it into place, so a reader never sees half an export. Files are 0600 in a 0700 directory: they hold conversation text. The export is deterministic: the same dataset and ledger give the same bytes (rows in item-ID or unit-ID order, JSON with sorted keys, no timestamps of its own), and `EXPORT_ID` is derived from the files' SHA-256 hashes, so exporting again is a no-op, but only after every file already there has been checked against its manifest hash: a damaged export (a truncated file, say) or a different one at the target is refused, and `--replace` rewrites it: the new export is built beside it, the old directory is renamed aside, the new one renamed into place, and only then is the old one deleted, so a failure leaves one complete export. `--replace` refuses a directory holding files the old export's manifest does not list (a saved smoke model, say) unless `--force-replace` is given too. A job labeled under a taxonomy other than this build's (by its stored SHA-256) is refused: ancestors, masks and support would be computed from the wrong tree. A job still running, or not finished, is exported as it stands: items without a settled result are `unlabeled`, and the manifest's `job.complete` is false with `job.incomplete_reasons` naming what is open (requests pending, in flight, held, waiting on a suspected refusal (`waiting_suspicion`), stopped, unknown or failed; a request whose items were all refused elsewhere is settled, items `unlabeled` or `blocked_oversize`, an incomplete selection); the counts are in `heldout-manifest.json` (`job_wide`), since they span held-out items. Because the exports directory is not part of a dataset, `prepare --replace` refuses a dataset that has one.

The items are every item the job requested or holds a result for (imported results included). Each appears once in each per-item file:

| File | One row per | Holds |
|---|---|---|
| `inputs.jsonl` | item | only what a student sees at inference time |
| `provenance.jsonl` | item | where the item came from; no labels |
| `labels.jsonl` | item in `train` or `dev` | the teacher's result |
| `labels-heldout.jsonl` | item in `test`, `fresh`, `quarantine` or without a split (`unassigned`) | the teacher's result |
| `unit-labels.jsonl`, `unit-labels-heldout.jsonl` | chunked unit, by its split | the chunks' merged labels |
| `export-manifest.json` | | versions, every file's hash, rules, and aggregates of the training splits only |
| `heldout-manifest.json` | | aggregates of the held-out splits (support, outcomes, strata, coverage) |

**`inputs.jsonl`**: `item_id`, `dataset_id` (the first 16 hex digits of the dataset manifest's SHA-256), `units_version`, `unit_id`, `split`, `cohort`, `actor_kind`, `sender` (the role the prompt names), `provider`, `kind`, `channel`, `reasoning_format`, `depth` (null if unresolved), `text` (the model-visible CURRENT_TEXT, markers included), `context` (the PREVIOUS_CONTEXT the teacher saw: the last 600 characters), `context_excerpt` (whether that cut removed anything), `chunk_index`, `chunk_count`, `chars`. Nothing else: no labels, teacher identity, evidence, rationale, outcome, family, duplicate or leakage marks, and no later message (context is built only from earlier ones). The split is derived from family IDs and time, never from labels.

**`labels.jsonl` / `labels-heldout.jsonl`**: `item_id`, `unit_id`, `split`, and

- `status`: `usable`, `usable_need_context` (a usable result whose teacher said preceding context mattered), `refused`, `refusal_suspected`, `invalid`, `tool_use` (an invalid result because a tool was used), `missing`, `held`, `transform_unverified` (a decoded piece of the item, such as a feedback comment or delegation payload, no longer decodes from its encoded message bytes to exactly the text shown, so its labels are not published), `unlabeled` (no settled result yet: the request is pending, in flight, unknown, failed or stopped, or the reply was a suspected refusal held for review), `refused_elsewhere` (not sent because a refusal recorded for the same material blocks it, including items skipped when the job was created), `blocked_oversize`, or any other outcome the ledger records (for example `refused_elsewhere` or `blocked_oversize`), carried as is: never usable, never negative. Only `usable` and `usable_need_context` rows carry labels; they stay distinct so a trainer decides about the second (below). `outcome` is the ledger's item outcome (`usable_with_evidence_issues` is exported as `usable`, its unsupported labels set apart) or `no_result`.
- `labels`: the positives, accepted labels whose evidence is `supported` (a valid quote inside a target piece), leaves or broad parents exactly as returned. `unsupported_labels` maps other accepted labels to their evidence status (`in_marker`, `in_context`, `not_found`, `missing`, …): not positives, not negatives. `uncertain_labels`: not positives, not negatives. `implied_ancestors`: the positives' ancestors, listed apart. They are positives for the ancestor's own classifier, since the taxonomy implies ancestors. `masked_labels`: the labels the row says nothing about (neither positive nor negative): every uncertain and unsupported label with all its ancestors and descendants (an uncertain leaf implies its parent, so the parent cannot be a negative either), and every descendant of a positive (a returned broad parent leaves its subtype open, so it is never a positive for its children), less the positives and their ancestors. Evidence statuses that are not `supported`, such as `ambiguous_mixed` (a quote found both in the person's text and in excluded material), make a label unsupported. These five are `null` unless the status is `usable` or `usable_need_context`: a refused, invalid, missing, held or unlabeled item is present with its status and never an all-negative row. What the teacher returned for such a row (for example a held result) is under `returned`, and `reason` says why it has no labels (its issues, such as the refusal that blocked it, or the state of the request it waits in).
- `need_context`, `evidence` exactly as the ledger stored it (each quote with its validation status and every occurrence: `item_start`/`item_end` byte offsets into the item text and a status; a `valid` occurrence carries the original message ranges, a rejected one (`in_marker`, `outside_target`, `spans_pieces`, …) has none. Only labels whose evidence status is `supported` become positives, whatever occurrences they list), `issues` (the validation issues), and `flags`: `refused_copacked_unresolved`, `served_model_differs`, `served_model_unverified` (every Codex result), `served_model_accepted`, `answer_without_terminal`, `usage_missing`, `imported`.
- `teacher`: job, route, model, effort, served-model status of the job, CLI version of the attempt, prompt, schema and taxonomy versions.
- `receipt`: the result's `request_id`, `attempt_id`, `imported_from`, `request_state`, `request_items`, `contract_hash`, the attempt's `cost_status` (the worst of its usage rows, in this order: `priced`, `assumed`, `estimated`, `estimated_upper_bound` (only in ledgers priced under pricing-v4), `partial`, `unpriced`, then any status this export does not know; or `no_usage`, `imported`), `attempt_estimate_usd` and `estimate_basis` (since pricing-v5, usage that cannot be priced keeps an estimate and how it was made beside it, never as its cost: exposure, not known spend; null and empty for older ledgers) and `attempt_cost_usd` (the whole request's cost, shared by its items), the requests the item was in, and `history`: every result the job holds for the item (attempt, request, outcome, time). When an item has several results (retries, imports), the authoritative one is the latest usable result, else the latest result of any outcome.

**`provenance.jsonl`**: `item_id`, `unit_id`, `split`, `family_id`, the source `message_id`, `conversation_id`, `canonical_conversation_id`, `workspace_id`, `root_conversation_id`, `run_id`, `session_id`, `session_role`, `depth_status`, `created_at`, `content_hash`, `message_sha256`, `authorship_reason`, `length_bucket`, `target_hash`, `duplicate_of` and `duplicate_relation` (delegation copies, later fork copies: drop them to count a text once), `cross_split_duplicate`, `seen_in_train`, `common_short_text`, `visible_range` (the item's bytes in the unit's visible text), `markers` (item-relative byte ranges of `⟦…⟧` markers), `source_ranges`, the unit's `pieces` (role, status, category, reason, original and visible byte ranges, transform, re-use source), its `sentences` (`sentences-v1`, original byte ranges), the message's `actions` (question forms and tool-result answers) and `context_refs`. A literal source range is `{start, end, item_start, item_end, sha256}`: bytes `start..end` of the stored message equal bytes `item_start..item_end` of the item text, whose SHA-256 is given (the export checks the equality before writing; the message itself is not exported, since its other pieces may be secrets or pasted material). A transformed range (`json-string-v1`: a feedback comment or delegation payload shown decoded) is `{start, end, transform, item_start, item_end, source_sha256, piece_sha256, whole_piece, transform_verified}`: the encoded bytes of the message map to the whole decoded piece, never to offsets inside it. Text that was not valid UTF-8 never reaches an export: `prepare` excludes such messages (`invalid_utf8`), and export refuses any item, context or evidence that is not valid UTF-8 or whose offsets do not fall on character boundaries, rather than replacing bytes.

**`unit-labels*.jsonl`**: for each chunked unit with an item in the job: `unit_id`, `split`, `chunking_version`, `merge_version` (`chunk-union-v1`), `unvalidated_merge: true`, `chunk_count`, `chunks` (item, index, status, labels) and, when every chunk is in the job and labeled, `status: usable` (`usable_need_context` if any chunk needed context) with the union of the chunks' positives, their unsupported and uncertain labels minus the positives, implied ancestors, masked labels and whether any chunk needed context; otherwise `status: partial` and null labels. The merge has not been validated against labels of whole long messages: negation, permission scope and references can cross a chunk boundary.

**`export-manifest.json`**: `export_version`, `export_id`, a population statement, the dataset (ID, manifest hash, population, snapshot, contracts), the job (route, model, effort, served-model status, prompt, schema and taxonomy versions and hashes, `complete` and `incomplete_reasons`), the contract versions, `files` (SHA-256 and bytes of every file, including the held-out ones and `heldout-manifest.json`, and rows of each JSON-lines file), `training_files` and `heldout_files`, `training_splits` and `heldout_splits`, `items`, `families_in_several_splits` (0 by construction), the `taxonomy` (each label's parent), the `rules` in prose, and aggregates of the training splits (`train`, `dev`) only: `counts` (items by split, cohort, provider, depth, length bucket and ledger outcome, each by status), `label_support` (for every taxonomy label, zero-support labels included, per split: `positive`, `unsupported`, `uncertain`, `implied` and `masked` counts over `usable` rows, and the same five prefixed `need_context_` over `usable_need_context` rows), `strata` (per split: duplicates, `seen_in_train`, `common_short_text`, `cross_split_duplicate`), `coverage` (items present without labels, by status, and `refused_copacked_unresolved`: refused items packed with others, whose refusal may belong to a neighbour yet which stay blocked on every route), `flags`, `families_by_split`, `chunked_units` and `transforms` (verified and unverified decodings). `heldout-manifest.json` holds the same aggregates for the held-out splits and, under `job_wide`, what spans both sides: the job's request states, its selection (with skip counts) and the counts behind `incomplete_reasons`, so a trainer that reads the export manifest learns nothing about held-out labels, not even their counts. Attempt cost statuses the export does not know (a newer pricing rule's) rank worst, so they are never hidden behind `priced`.

### Consuming an export

A training project needs no Pharos code: JSON lines and the manifest are enough.

1. Check the files against the manifest's hashes.
2. For training, read `inputs.jsonl`, `provenance.jsonl`, `labels.jsonl` (and `unit-labels.jsonl` for whole long messages) and `export-manifest.json` only. Train on `train`, tune on `dev`. Never open the `-heldout` files or `heldout-manifest.json` until final evaluation.
3. Use rows whose `status` is `usable`. For each label, a row is positive when the label is in `labels` or `implied_ancestors`; it says nothing (exclude it for that label) when the label is in `masked_labels`; otherwise it is negative. `usable_need_context` rows carry real teacher labels, but the teacher said the 600 characters of context were not enough. Leaving them out is not neutral: they are disproportionately short human replies ("yes", "do it", "the second one"; 14 of 41 items, 34%, in the 2026-10-27 Haiku pilot), so excluding them biases a student away from exactly those. Whichever choice a trainer makes it should report it; the fix is a later experiment with longer context, not dropping them silently.
4. Drop rows with `duplicate_of`. Splits follow families (`family_id`), so a parent and child, a fork, a mirror or copied text never straddle train and test; quarantine is neither.
5. Evaluate on `test` and `fresh` from `labels-heldout.jsonl`, excluding `seen_in_train` rows (their text of 40 or more characters also occurs in train) and reporting `common_short_text` rows ("continue", "yes") as their own stratum. Report support per label: rare labels need targeted review, not a score.

The labels are a teacher model's provisional labels, not reviewed truth, and the export describes the job's selection, not the library.

### Smoke check and Go parity

`python3 tools/labeling_smoke.py EXPORT_DIR [--out model.json] [--report report.json]` (Python 3 standard library only) is a smoke check of the export and the training path, not a quality claim. It verifies the manifest and every file hash, that inputs carry only student fields, that each item has one label row in the file its split belongs to and that only `usable` and `usable_need_context` rows have labels (with `implied_ancestors` and `masked_labels`), and round-trips every byte range (source ranges against their SHA-256, markers, evidence quotes) as strict UTF-8. It then fits a one-vs-rest logistic regression (SGD, 8 epochs, learning rate 0.5, L2 1e-4, seed 20261027) on hashed character n-grams: code points 2 to 4, A-Z lowercased and nothing else (so Turkish İ stays İ), each n-gram's UTF-8 bytes hashed with FNV-1a 64 into 2^18 buckets, counts L2-normalized. It trains on usable `train` rows of `labels.jsonl` with the rule above, leaving out `usable_need_context` rows unless `--include-need-context` is given; the report and its summary say how many rows that removed and their cohorts and length buckets; the held-out files are opened only by the evaluation, after training (a unit test fails training if it opens one). It evaluates on `test` and `fresh` per label (support, precision, recall, F1 at 0.5; labels with fewer than 3 positives are reported as unsupported, not scored; micro and macro over scored labels), overall, for `common_short_text` and for the rest, listing every taxonomy label (one without positives as unscored with support 0), and writes the model (featurizer spec, bias and sparse weights per label) and a report. Below 200 train rows or 50 evaluation rows it says the data is too small to mean anything, and still runs every structural check.

`internal/archive/labeling_smoke_model.go` loads that model in Go (refusing any other featurizer) and scores text with the same featurizer. `testdata/labeling-parity.json` holds invented strings (combining marks, astral emoji, ZWJ sequences, flags and variation selectors, Hebrew and Arabic with RLM, Turkish İ/ı, CRLF, tabs, NBSP, non-ASCII capitals, CJK, a `⟦…⟧` marker, U+2028/2029, empty and one-character text), a tiny model, FNV-1a reference values, and the feature indices, values and scores Python computes; the Go and Python tests both check them (indices and values exactly, scores within 1e-9). This fixture covers the smoke featurizer only.

**Production student.** Any later student model must ship its own parity fixture for its tokenizer and text normalization (lowercasing, Unicode normalization, whitespace and control handling, truncation), checked in both its training environment and the Go (or other) runtime that will score text, before a long training run. Passing this repository's fixture says nothing about a different tokenizer.

## Known limits

- Human pieces inherit the classifier's limits: typed text is an estimate, and prose written elsewhere and pasted without cues still counts as typed.
- Embedded sub-agent sessions are identified by the session ownership the catalog records; a sub-agent prompt stored as a user message outside such a session is treated as the classifier treats it.
- The chunk merge (`chunk-union-v1`) is unvalidated, and export does not merge partially labeled units.
- Re-sent text whose copied passage occurs in its source more than once with different attributions is unverified context, and so is any re-sent text from an embedded sub-agent's prompt.
- Delegation duplicates are found only through a recorded delegation-to-child link (results through the delegation's call ID).
- Inherited history is recognized by identical text only; a fork that reformats its copy is not recognized.
- Preparing even a restricted sample classifies every user message in the library, since copies and templates are found across all of them.
