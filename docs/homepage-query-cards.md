# Homepage query card implementation tracker

The homepage uses URL bookmarks and the retained Query Table V3 snapshot. It ships 59 executable recipes; 57 open row-producing grouped comparisons. All 96 original concepts remain below, with their richer requested behavior and blockers preserved. “Partial implementation” means the current card answers a narrower observed question; it does not claim to deliver the complete original concept.

Recommendations require matching results in explicit 1, 7, 30 or 90 day lookbacks. New queries store native datetime operands such as `>= -7d` and `< +0s` in URLs, snapshots and saved views. These are elapsed windows through execution time, rather than midnight-aligned calendar spans. A day means 24 hours across daylight-saving changes. Usage is filtered at its recorded fact grain and is not prorated into imaginary partial rows. Old bookmarks explicitly marked as rolling are migrated to native operands; intentionally fixed saved ranges remain intact. Titles, descriptions, ordering and collected cover settings use `pharos-bookmarks-v1`; old saved-query IDs are preserved.

The machine-readable companion [homepage-query-cards.json](homepage-query-cards.json) retains every original recipe, eligibility rule, proposed preview, implementation mapping and capability request. Update both files when a deferred card is implemented.

## Card library and editing (October 2026)

Home's **Browse the card library** link opens `/home?cards=library`. All 59 definitions remain visible, including empty and unavailable cards. Search, data source, topic, card kind and sorting controls make it possible to review them together. Filters persist in the address. The preview window is shared for comparison.

**Edit card** changes the question, description, default lookback, cover metric and chart. Overrides are library preferences in `pharos-card-templates-v1`, and apply to future suggestions and collections; Reset template restores the shipped definition. Collected cards retain their own cover settings. The editor names the destination's dimensions and links to the Query Table editor for grouping/filter/column changes. Collection writes the durable query link before publishing the bookmark, and surfaces failures in the library.

Loading covers preview the saved display shape before data arrives. The library,
collection and conveyor use `cardLoadingPresentation` to project the same chosen
cover metric as the finished preview. Configured group limits control placeholder
bar/row counts; histograms use their bin count, and daily timelines reserve their
headline and calendar bars. Values pulse as a single box, scatter dots gently
drift, and lists, lines, box plots, pies/rings and text have corresponding shapes.
Marks remain decorative: no guessed values or sample counts are displayed.
The existing 0.8-second spinner and 1.5-second pulse cadence are retained, and
reduced-motion preferences stop all animation. Result-dependent scalar collapse
still happens once the returned groups are known.

A template separates its question, cover and destination. `cardCoverQuery` builds a transient chart query from the saved destination. Result covers aggregate the grouped summaries and preserve HAVING, so a failure-rate chart uses the same eligible tools as the comparison table. Source covers retain raw observation distributions or paired axes: a duration box plot opens command rows with median, maximum, total and count; a pricing scatter opens repository price-comparison rows. Selecting a source metric with different dimensions also changes the destination keys to those dimensions. Source plots describe observations before any grouped HAVING predicates.

Ranked covers draw labelled bars with compact units and supporting counts. Daily covers retain timeline marks; distribution and scatter plots retain their native chart forms. Work titles are projected from representative rows for chart labels, while workspace IDs preserve identity. Every grouped table offers **Records**, restoring the source layout/metrics with the group's full key tuple added to its source filters. Null keys become IS NULL. Rates, medians and distinct counts are never summed into fictitious totals.

Repeated errors, searches and reads require two records. Failure rates include successful calls and require ten calls plus at least one failure. Thresholds are visible and editable in the destination. Context/output attribution does not establish waste; co-issued tools do not establish simultaneous execution.

## Cards from recent Pharos additions

- **Reasoning effort:** API equivalent, tokens, reasoning tokens and distinct sessions by provider/model/effort; missing effort remains a cohort.
- **Harness versions:** first/last recorded harness-version cohorts, retaining transitions and unknown versions.
- **Delegation depth:** attributed subagent tokens, API equivalent and distinct sessions by provider/depth.
- **Pricing coverage:** priced, partial, assumed and unpriced tokens remain separate.
- **Co-issued tools:** call counts, mean request batch size and failures, without implying elapsed overlap.
- **MCP responses:** measured response bytes, errors and truncations per Pharos MCP tool.

Carbon estimates and timed session parallelism were reviewed. Their calculation/provenance APIs are not generic Query Table fields yet; adding approximate token-based substitutes would misrepresent those features. They remain candidates for a typed calculation relation or dedicated card adapter.

## Wishlist capacity audit (October 14, 2026)

All 96 original ideas were checked against actual SQL bindings and negotiated V3 capabilities. Sixteen additional recipes bring the library to 59 cards: 57 grouped destinations, one literal-correction view and one local-hour writing timeline. 41 ideas now have shipped observed variants; 55 still require new facts or a dedicated adapter. The original intended recipe/eligibility stays intact in the JSON; every idea also carries a dated `capacity_audit` and its remaining gap.

The additions cover exact repeated human messages; human-message counts per conversation and a histogram of those counts; positive-feedback, example and reported-action phrase candidates; skill body bytes and distinct file reloads; explicit zero-item Pharos MCP searches; repeated path edits; setup/access failure candidates; exact repeated failing commands; TL1 revisits and mixed candidate dispositions; primary recorded URLs; writing by canonical work; and local-hour writing. Covers and destinations use the same window and evidence filters. Histogram samples are conversation totals, not individual messages or word counts. Local-hour queries capture the device's IANA timezone when instantiated; saved links preserve it, including repeated hours at daylight-saving transitions.

Literal matches remain candidates for inspection. They are not semantic labels or final acceptance. Exact command repetition is not a retry episode; edit counts are not net changes; mixed TL1 dispositions are not simultaneous model disagreement; supplied URLs do not prove a page was read. These boundaries appear on the cards and in the per-idea backlog.

The deferred ideas predominantly need ordered recovery/check/approval/resume episodes, comparable task/outcome annotations, lineage/co-change relations, interval unions, aligned change cohorts, or scenario inputs. The existing carbon/concurrency APIs need a faithful typed card adapter. Per-call tool dollars are still priced **after paging** (`aggregate.measure=false`, no SQL binding); neither totals nor failure-episode costs can be derived by aggregating those displayed values.

The real-library audit also checked the new recipes at 30 and 90 days. Primary-URL and exact repeated-failing-command previews can exceed the 15-second preview budget at 90 days. Their suggestion defaults use 7/30-day windows; longer windows remain available for direct exploration. No other new recipe reported an error in that audit.

## Integration stages

1. Integrated: local Miami V3 SQLite/map execution, canonical computed metadata/revisions, admitted computed source filters, row-producing groups/HAVING, result-stage distributions, timezone-aware calendar metrics and compact native covers.
2. Preview scheduling: compatible metrics share one request and snapshot, with unique wire IDs and a maximum of 20 metrics per batch. Three workers bound scans; cached results retain all metric payloads for one minute. Metadata refreshes on each uncached run. Leaving Home cancels work. Local diagnostics and definitively rejected batches isolate failing cards.
3. Remaining: derived message, episode, interval, task/cohort and lineage datasets; bounded evidence hydration; arbitrary percentiles, heatmaps and typed adapter seams where the full ideas need them.

Each HTTP preview request has a 15-second deadline. Saved queries keep their scope, including shown-row pages; suggested metrics default to all matching rows. A bookmark's optional cover metric ID changes only its preview. Compact native covers show at most four result groups (24 for scatter/line/vertical bars), disclose that budget, and retain complete returned results for selection; the full view keeps every saved metric. Existing daily Usage columns retain local-calendar gaps, the shared palette and an exact Other series.

Recommendation-specific eligibility is evaluated separately from saved-view readiness. Empty saved views remain in the collection; zero rates with observations are valid saved results. Rates include denominators, distinct counts and medians are never summed into invented totals, and computational coverage does not establish source completeness. TL1 rates retain project/flavor/execution-class/version/configuration cohorts at attempt grain. Price comparison uses only historical and today-priced retained usage. Recently active work costs cover its lifetime. Repeated read counts do not establish unchanged-content retries. Distribution comparisons make no automatic statistical or causal claim.
